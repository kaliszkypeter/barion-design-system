KYB field-diff layout options

Three structural approaches to comparing merchant-submitted data against the trade register API, for the compliance officer reviewing "Business & company data" during KYB verification. Each option renders all 5 compared fields in the proposed state (not yet written), plus a smaller demo of the same option in the committed state (after approval, authoritative value written, replaced value shown as history). Tokens only from brand-tokens.css — no hardcoded values.

Option A

Stacked label → submitted → register

Each field is its own small card: label on top, submitted value, then the register value directly beneath in the same column — so both are read top-to-bottom in place, no need to scan sideways or align across a row. Only fields that differ get a highlighted card border and background; matches stay flat and quiet.

Trades off: very easy to scan one field in isolation (great for the officer clicking into a single flagged row), but the 2-line "submitted → register" card is noticeably taller than a plain row, so the grid needs more vertical space and can't compress five fields into one glance the way a table can. Best when the officer is resolving one field at a time, weaker for a fast top-to-bottom pass of the whole section.
Option B

Two-column submitted vs. register table

One row per field, submitted and register values in fixed side-by-side columns so the same physical position in every row is directly comparable — the eye tracks one horizontal line rather than re-finding the pair each time. A left accent bar plus a soft highlight on both cells marks a differing row; a status icon column removes any need to read both columns when they match.

Trades off: the fastest layout for a full top-to-bottom scan — every field is one row, matches take almost zero attention, and the eye never has to relocate the comparison point. The cost is horizontal space: two full-width text columns plus a status column is tight at 768px, and the long organization name forces every row in the table to reflow to its height (a table row's height is shared, so one long field taxes the whole table, not just its own row).
Option C

Single value, inline diff highlight + expandable detail

The field shows only the submitted value plus a status icon — visually identical to a normal read-only field, so a quiet pass over matches costs nothing. A differing field adds a small "What changed" disclosure; opened, it shows the register value with only the changed substring highlighted, so the officer reads "…Zrt." → "…Zártkörűen Működő Részvénytársaság" as a targeted edit, not two full strings to re-diff by eye.
